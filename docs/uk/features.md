# Функції після PoC

Обидві функції будуються на генераторі з [outfit-algorithm.md](outfit-algorithm.md#інтерфейс-генератора): він приймає речі списком і вміє `mustInclude` / `exclude`. Якщо це закладено на кроці 1, обидві додаються без переробок ядра.

## Перевірка перед покупкою

**Сценарій:** у магазині фотографуєте річ → за кілька секунд бачите:
1. скільки хороших образів вона дає з вашим гардеробом, і 3–5 найкращих на 2D-ляльці;
2. схожі речі, що у вас уже є («у вас уже 5 чорних футболок»);
3. вердикт: «Брати» / «Подумати» / «У вас уже є схоже».

### Як працює

1. **Фото → видалення фону → теги.** Автотеги дуже бажані: заповнювати форму вручну в магазині незручно. Без них — коротка форма з трьох полів: слот, колір, формальність. Теги — тим самим ендпоінтом, що й для звичайних речей ([auto-tagging.md](auto-tagging.md#потік)); фото при цьому ніде не зберігається.
2. **«Віртуальна» річ.** Не зберігається в гардеробі (або зберігається зі статусом `wishlist`, щоб вирішити пізніше).
3. **Генератор з `mustInclude: [нова річ]`** проти ваших реальних речей → кількість образів з оцінкою вище порогу + найкращі з них.
4. **Приріст — головна метрика:** скільки нових хороших образів з'являється завдяки цій речі. Річ, яка дає 12 нових образів, корисніша за ту, що дає 2.
5. **Схожість:** той самий слот і тип + близький колір (відстань у колірному просторі Lab, а не RGB — вона ближча до людського сприйняття) + спільні стилі.

### Коли додавати і наскільки складно

Після генератора (крок 10), бажано після автотегів (крок 15). Якщо генератор — чиста функція з `mustInclude`, це приблизно **кілька днів роботи**: один ендпоінт, один екран, функція схожості. `wishlist` додається як ще одне значення `Item.status`.

## Валіза в подорож

**Вхід:** місто; дати; які дні які нагоди (за замовчуванням — «щодня», можна позначити «робота», «вечірка»); обмеження (напр. «ручна поклажа» → не більше N речей; чи буде прання).

### Як працює

1. **Погода.** Місто → координати ([Open-Meteo](https://open-meteo.com/) Geocoding) → прогноз на дні поїздки (до ~16 днів наперед). Для дальших дат — середні значення за ті самі дати минулих років з архіву погоди. Open-Meteo безкоштовний для некомерційного використання й без ключа. Для кожного дня — мінімальна й максимальна температура та опади → яка теплота одягу потрібна і чи потрібен верхній одяг.
2. **Вимоги днів.** Список того, що треба «закрити»: день × нагода × погода.
3. **Кандидати.** Лише речі, що підходять хоча б одному дню за теплотою й нагодою.
4. **Мінімальний набір.** Це задача з родини «покриття множини»: точний розв'язок дорогий, але для гардероба вистачає жадібного підходу:
   - порахувати «універсальність» кожної речі — зі скількома кандидатами вона дає хороші пари;
   - по одній додавати річ, яка «закриває» найбільше ще не закритих днів (або дає найбільше нових хороших образів) відносно своєї «ваги»;
   - коли всі дні закриті — спробувати по черзі викинути кожну річ: якщо дні лишаються закритими, викинути;
   - взуття рахувати «важчим» — воно об'ємне.
5. **Розклад.** Для кожного дня — образ лише з речей набору, без однакових образів поспіль.
6. **Результат:**
   - список для пакування з галочками;
   - календар образів по днях;
   - «8 речей → 12 образів»;
   - що вдягнути в дорогу (найоб'ємніше — на себе).

### Чого навчить

- Зовнішні API з кешуванням відповідей.
- Оптимізаційні евристики.
- Тестування алгоритму на підготовлених даних: `planTrip(items, days, constraints)` — чиста функція в `core`.
- Опційне ускладнення — точний розв'язувач через цілочисельне лінійне програмування.

### Коли додавати

Після генератора, разом із загальною функцією «погода» — вона знадобиться й для щоденного образу.
