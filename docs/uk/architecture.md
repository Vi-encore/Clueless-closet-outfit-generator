# Архітектура

> Відкинуті альтернативи й порівняння (AWS Free Tier, Supabase, DynamoDB, хостинг) — у [backend-options.md](backend-options.md). Сутності й поля — у [data-model.md](data-model.md).

## Вимоги

- **Кілька користувачів**, у кожного свій акаунт і свій гардероб.
- **Телефон і комп'ютер.** Речі фотографуються телефоном.
- **Фото приватні:** їх бачить лише власник (пізніше — ще й той, кому річ позичено).
- **AI-функції** (автотеги, try-on) → ключі лише на сервері, ліміти на кожного користувача.
- **Власний бекенд на NestJS** — заради практики.
- **Мінімальні витрати:** на старті все на безкоштовних тарифах.

## Схема

```
PWA (телефон / ноутбук) ──REST + JWT──► NestJS API ──► PostgreSQL (Neon)
  │                                        │  ▲
  │                                        │  │ задача ▼ / webhook ▲
  │                                        │  │
  │                                        │  Modal: Python + GPU (try-on)
  │                                        │  ──► сховище за presigned URL
  │                                        │
  │                                        ├──► Gemini free tier (автотеги)
  │                                        │
  │                                        └──► видає presigned URL
  │
  └──── PUT / GET за presigned URL ────► Об'єктне сховище, S3 API
                                          (Cloudflare R2 або AWS S3)
```

Модулі API:

| Модуль | Що робить |
|---|---|
| `auth` | Реєстрація, вхід, JWT, refresh-токени |
| `users` | Профіль, пошук за username (пізніше — друзі) |
| `items` | Гардероб, фото, статуси, архів |
| `outfits` | Генерація (через пакет `core`), збереження, реакції, «вдягнуто сьогодні» |
| `occasions` | Системні й власні нагоди |
| `ai` | Автотеги, try-on-задачі через `TryOnProvider` (Modal), webhook для результатів, ліміти використання |
| `loans` | Позичання речей (пізніше) |
| `storage` | Presigned URLs, видалення файлів |

## Стек

| Шар | Вибір | Чому |
|---|---|---|
| Клієнт | React + Vite + TypeScript, PWA | Один код для телефона й комп'ютера; камера через `<input type="file" capture>` |
| UI | 98.css + Tailwind CSS v4, власні компоненти | Ретро-вигляд без JS; Tailwind — для розкладки. Деталі — в [ui.md](ui.md) |
| API | NestJS | Практика бекенду: модулі, DI, guards, DTO й валідація |
| ORM | Prisma | Типізований клієнт, міграції, є рецепт в офіційній документації Nest |
| База | PostgreSQL на Neon | Безкоштовно назавжди (0.5 ГБ); після сну прокидається сама |
| Файли | S3 API: Cloudflare R2 (або Backblaze B2 / AWS S3) | R2 — 10 ГБ безкоштовно й без плати за трафік, але потрібна картка; B2 — 10 ГБ без картки. Код однаковий для всіх |
| Авторизація | Власна в Nest: Passport + JWT | Ключова частина практики |
| Алгоритм | `packages/core` — чистий TS | Не залежить ні від Nest, ні від бази; легко тестувати |
| Try-on | CatVTON (Python) на Modal — serverless GPU | $30 безкоштовних кредитів / міс; потрібна картка + ліміт витрат. Деталі — в [try-on.md](try-on.md) |
| Монорепо | pnpm workspaces | Спільні типи між `web`, `api` і `core` |

## Ключові рішення

### TypeScript усюди

- Одна мова для клієнта, API й алгоритму; доменні типи (`Item`, `Outfit`, `Occasion`) описуються один раз.
- У моделі речі багато перелічуваних значень — TS ловить помилки на кшталт `"casul"` ще до запуску.
- Обчислення легкі (10 000 пар — мілісекунди), машинне навчання не потрібне, тож Python теж.

### PostgreSQL

Дані реляційні: речі ↔ образи ↔ історія ↔ нагоди, а з кількома користувачами — ще й зв'язки між людьми (позичання, друзі). Чому не DynamoDB — див. [backend-options.md](backend-options.md#чому-не-dynamodb).

### Алгоритм працює на сервері

`POST /outfits/generate { occasionId }` → сервіс бере доступні речі користувача (без тих, що в пранні, в архіві чи позичені), історію й реакції → викликає `core.generateOutfit()`.

- Історія й лайки вже в базі — не треба тягнути їх на клієнт.
- Правила доступності (позичання тощо) в одному місці.
- Клієнт тонкий. `core` чистий, тож за потреби (офлайн) його можна запустити й на клієнті.

### Фото йдуть напряму в сховище

1. Клієнт прибирає фон (`@imgly/background-removal`) і стискає фото у WebP.
2. `POST /items/upload-url` → API перевіряє ліміти й повертає presigned PUT URL (дійсний кілька хвилин).
3. Клієнт вантажить файл напряму в R2 / S3 — через API файли не проходять.
4. `POST /items` з ключем файлу → API створює річ.

Для показу API видає presigned GET URLs лише для речей, до яких користувач має доступ.

### Мобільний застосунок: PWA зараз, магазини — через Capacitor

**PWA покриває все, що потрібно зараз:** встановлення на головний екран, повноекранний режим, камера, завантаження фото, Web Share, а згодом — push-сповіщення (на iPhone — лише для встановленої PWA, iOS 16.4+). На iPhone встановлення ручне: Safari → «Поділитися» → «На початковий екран».

**Якщо знадобляться App Store / Google Play** — той самий React-білд обгортається в [Capacitor](https://capacitorjs.com/) (нативна оболонка з WebView). Це не переписування, але доведеться:
- згенерувати нативні проєкти (`android/`, `ios/`), іконки, splash-екрани;
- замінити частину веб-API на плагіни Capacitor (камера, push, файли);
- змінити зберігання refresh-токена (у WebView cookie на інший домен працюють ненадійно — див. [Авторизацію](#авторизація));
- заплатити за акаунти розробника: Google Play — одноразово, Apple — щороку; для збірки під iOS потрібен Mac (або платний хмарний білд).

Для власного Android-телефона платити не обов'язково: APK можна зібрати в Android Studio на Windows і встановити напряму.

Особливості Android і iPhone та як тестувати на обох — у [mobile.md](mobile.md).

**Що закладаємо одразу, щоб перехід був дешевим:**
- **Mobile-first верстка:** спершу телефон; кнопки ≥ 44 px; врахувати «чубчик» і жести (`viewport-fit=cover`, `env(safe-area-inset-*)`); нічого, що працює лише при наведенні мишею.
- **PWA з першого дня:** маніфест, іконки, `display: standalone`, service worker (`vite-plugin-pwa`).
- **Платформні функції — за тонкими обгортками:** `camera`, `tokenStore`, `share`, `notifications` — окремі модулі з простим інтерфейсом. Перехід на Capacitor змінить лише їх (та сама ідея, що `StorageService` і `TryOnProvider` на бекенді).
- **Адреса API — з конфігурації** (`VITE_API_URL`; у розробці — `/api` через проксі Vite). У нативній оболонці проксі немає.

### Авторизація

- Email + пароль; хеш — argon2.
- Access token (JWT, ~15 хв) + refresh token (httpOnly cookie, ротація, у базі зберігається лише хеш).
- Endpoint оновлення токенів проєктуємо так, щоб refresh-токен міг прийти або з cookie (веб / PWA), або в тілі запиту (майбутня нативна обгортка, де токен лежить у захищеному сховищі пристрою). На клієнті це ховається за `tokenStore`.
- Пізніше: вхід через Google (Passport strategy), підтвердження email і скидання пароля (потрібен сервіс розсилки листів).
- Якщо власна авторизація забиратиме забагато часу — бібліотека Better Auth.

### Ізоляція даних користувачів

Кожна таблиця з даними користувача має `ownerId`, і кожен запит фільтрується за поточним користувачем.

Найчастіша помилка в багатокористувацьких застосунках — забути цю перевірку й віддати чужу річ за її id (IDOR). Захист:
- доступ до речей лише через методи на кшталт `findOwned(userId, itemId)`;
- e2e-тести на кшталт «користувач B не бачить і не може змінити речі користувача A».

### Ліміти й витрати

- Try-on забирає час GPU, автотеги — квоту безкоштовного тарифу (а на платних провайдерах — гроші) → добові ліміти на користувача (`UsageCounter`).
- Ліміт кількості речей / обсягу фото на користувача.
- Rate limiting на весь API (`@nestjs/throttler`).

### Довгі операції (try-on)

Генерація зображення триває від кількох секунд до хвилини (з холодним стартом). Процес:
- API створює `TryOnJob` зі статусом `pending` і викликає Modal-ендпоінт, передаючи presigned URLs (Modal не отримує ключів від сховища);
- Modal генерує у фоні, кладе результат за presigned PUT URL і викликає webhook `POST /internal/try-on-jobs/:id/complete` із секретним токеном;
- клієнт опитує статус задачі.

Схема й деталі — в [try-on.md](try-on.md#інтеграція-з-nestjs).

## Середовища

Для proof of concept без витрат і без картки — окремий план у [poc.md](poc.md).

| | Розробка | Продакшн (старт) |
|---|---|---|
| База | Postgres у Docker або окрема гілка в Neon | Neon, основна гілка |
| Файли | Окремий dev-бакет у R2 | Prod-бакет у R2 |
| API | Локально, `nest start --watch` | Render (безкоштовний інстанс засинає без запитів) → дешевий VPS, коли з'являться реальні користувачі |
| Клієнт | Vite dev server | Статичний хостинг (Cloudflare Pages, Netlify або Vercel) |

## Структура проєкту (чернетка)

```
apps/
  web/        React + Vite, PWA
  api/        NestJS
  tryon-modal/   Python: CatVTON як Modal-функція (поза pnpm workspaces)
packages/
  core/       доменні типи, скоринг, генератор + тести (Vitest)
docs/
```

## Безпека й приватність

- Бакети приватні; доступ лише через presigned URLs з коротким терміном дії.
- Ключі AI API й сховища — лише в змінних оточення API.
- Паролі — argon2; refresh-токени зберігаються хешованими.
- CORS — лише домен клієнта.
- Видалення акаунта видаляє всі дані й файли користувача.
- Фото, що надсилаються в AI API, підпадають під політику провайдера — це треба описати в політиці конфіденційності застосунку.
