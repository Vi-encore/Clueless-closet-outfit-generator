# Social features and real time

Mostly after the proof of concept; friends and a basic chat are already in the PoC (steps 6 and 8). The goal is useful scenarios between friends and practice with WebSocket / SSE.

## Scenarios

### Chat: why it is here

| Scenario | Summary | Why real time |
|---|---|---|
| **Chat about lending** | A conversation attached to a request like "lend me the red dress for Saturday": agree when to pick it up, remind about returning it | Live messages, "typing…", "read" |
| **"Help me pick an outfit"** | Send friends 2–3 outfit options for the evening — friends vote and comment (like Cher and Dionne) | The vote counter and comments update live |
| **"Cher" stylist bot** (optional) | Ask AI: "what should I wear to a job interview from what's in my wardrobe?" | The answer is "typed" as a stream (SSE) |

The most organic ones are the first two: they extend features already planned (lending, outfits) and only make sense between people.

### Likes, favorites, ratings

- **Favorites (your own):** a star on an item or outfit. Affects sorting and gives a small bonus in the generator's score ("favorite items show up more often"). The bonus has to be moderate so the generator doesn't show only favorites.
- **Ratings from others:** a like on an outfit / item that was shared with you. Shown as a counter; they affect your generator weakly or not at all — your own taste matters more.
- **Your own like / dislike of an outfit** is already in the model (`Outfit.reaction`) — that's a separate thing: training the generator to your taste.

## Technologies

| Technology | What it is | Where in the project |
|---|---|---|
| **WebSocket** (Nest gateways; the Socket.IO library) | A two-way persistent channel | Chat, "typing…", voting, live notifications |
| **SSE** (Server-Sent Events) | A one-way server → client stream over plain HTTP | Try-on status instead of polling, notifications, streaming AI answers |
| **gRPC** | Binary RPC between **services** (HTTP/2 + protobuf) | Not for the browser (that needs gRPC-Web + a proxy). The natural place is Nest ↔ the Python try-on worker (if it ever runs locally). Nest has `Transport.GRPC` in `@nestjs/microservices` |

**Socket.IO or plain `ws`:** Socket.IO gives ready-made rooms (room = conversation), delivery acknowledgements (acks) and automatic reconnection — more convenient for a chat. Plain `ws` teaches the protocol itself better. Nest supports both through adapters.

## How the chat works

1. The client connects to the WebSocket, passing the access token during the handshake (in Socket.IO — the `auth` field, not the URL).
2. The server verifies the token and joins the socket to the rooms of the conversations the user is a member of.
3. Sending a message: the server checks the sender is a member of the conversation (the same IDOR protection as in REST) → stores it in Postgres → broadcasts to the room → acknowledges to the sender (ack with the id).
4. History and missed messages come through REST with cursor pagination; after reconnecting, the client fetches everything newer than the last known message.
5. "Typing…" is a transient event, not written to the database.
6. "Read" is the member's `lastReadAt`; unread counts are derived from it.

What it teaches:
- authenticating WebSocket connections;
- rooms and broadcasting;
- delivery acknowledgements and retries without duplicates (the client generates the message id);
- reconnecting and fetching what was missed;
- rate limiting socket events.

Caveats:
- **Several API instances** need a shared bus between them (the Socket.IO Redis adapter). One instance is enough to start.
- **Cloudflare Quick Tunnel doesn't support SSE**, so test SSE locally or on hosting. WebSocket through the tunnel — check in practice.
- **Push notifications** (when the app is closed) are a separate technology (Web Push), see [mobile.md](mobile.md).

## Privacy and visibility

Until this stage everything is private. Social features need explicit visibility:

- `visibility` for outfits and items: `private` (default) → `friends` → (maybe later) `public`.
- **Friends only at first** — no public feed. That means less need for moderation.
- **Body photos (references, try-on results) are not shared by default.** Friends see the 2D doll on the mannequin or item photos; sharing a try-on of yourself is only an explicit action.
- Blocking (`Friendship.status = blocked`) and reporting a message.

## Data model (draft)

| Entity | Fields |
|---|---|
| `Conversation` | `id`, `type` (`direct` / `loan` / `advice`), `loanId?`, `adviceRequestId?`, `createdAt` |
| `ConversationMember` | `conversationId`, `userId`, `lastReadAt`, `mutedUntil?` |
| `Message` | `id` (generated by the client), `conversationId`, `senderId`, `body`, `attachment?` (a link to an item / outfit), `createdAt`, `editedAt?`, `deletedAt?` |
| `AdviceRequest` | `id`, `ownerId`, `outfitIds[]`, `question`, `closesAt` |
| `AdviceVote` | `adviceRequestId`, `voterId`, `outfitId` (one vote per person) |
| `Favorite` | `userId`, `targetType` (`item` / `outfit`), `targetId` |
| `Rating` | `userId`, `targetType`, `targetId`, `value` (like), `createdAt`; unique by (`userId`, `targetType`, `targetId`) |

Plus a `visibility` field on `Item` and `Outfit`.

## Order: from simple to complex

**In the PoC** (steps 6 and 8 of the [roadmap](roadmap.md)):
1. **Friends** (`Friendship`) — the basis for everything social.
2. **A basic chat between friends** (`direct`) — WebSocket, rooms, history, reconnection.

**After the PoC:**
3. **Favorites** — plain REST, no real time.
4. **SSE for try-on status and notifications.**
5. **Forwarding an item / outfit to the chat** — attachments with an access check.
6. **Chat about lending** — a conversation attached to an `ItemLoan`.
7. **"Help me pick an outfit"** — live voting.
8. **Ratings from friends.**
9. (Optional) **a stylist bot** with streaming answers, **gRPC** between Nest and the Python worker.

### What to lay down in advance

- `User.username`, UUIDs for all ids, `visibility` = `private` on `Item` / `Outfit` — step 3.
- Access token verification as a separate service method — step 4 (the gateway reuses it).
- Item / outfit access checks as separate methods — step 5 (chat attachments reuse them).
- A `realtime` module (the gateway only delivers events) separate from the domain `chat` module (logic and persistence). Then the same gateway can later deliver notifications and try-on status too. They talk through Nest internal events (`@nestjs/event-emitter`): `message.created`, `tryon.done`, `loan.requested`.
