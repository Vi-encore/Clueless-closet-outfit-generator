# Design

## Context

Step 2 of the roadmap. Motivation and scope: see proposal.md; requirements: see the delta specs.

Current state and facts that shape the approach (checked October 2026):
- `@closet/core` exports its TypeScript source (`"exports": "./src/index.ts"`) and uses extensionless relative imports. That works for Vitest and Vite, but not for Node, which will run the API.
- NestJS **12** is current. All its packages are ES modules; `nest new` asks whether to generate an ESM or a CommonJS project; ESM projects get Vitest instead of Jest.
- Nest 12 validates **Standard Schema** libraries natively: `@Body({ schema })` plus `StandardSchemaValidationPipe` from `@nestjs/common`. zod 4 implements Standard Schema.
- The Nest CLI and its schematics require Node **22.22.3+, 24.15+ or 26+**; this machine has 22.22.2.
- The Nest CLI ships with TypeScript 6; `core` uses TypeScript 7.
- `nestjs-zod` supports only Nest 10–11, so it isn't used.

## Goals / Non-Goals

**Goals:**
- Documentation that is generated from the validation schemas rather than written beside them.
- A running NestJS 12 app inside the pnpm workspace, with the Nest building blocks practised by hand: module, controller, service, dependency injection, a global pipe, configuration.
- One definition of valid data: request schemas are composed from `@closet/core` schemas.
- The API runs `@closet/core` as compiled JavaScript.

**Non-Goals:**
- Persistence, authentication, CORS, a global `/api` prefix (decided with the Vite proxy at step 8), deployment.

## Decisions

### 1. Node.js 24 LTS
Upgrade to Node 24 LTS: it satisfies every engine range in the stack and is supported until 2028.
- *Alternative — the latest 22.x (22.22.3+):* also works, but the 22 line leaves maintenance in April 2027.

### 2. An ESM Nest project, generated by the CLI
Generate `apps/api` with `nest new` and choose ESM. The whole workspace is already ES modules, and Nest 12 itself is ESM.
- *Alternative — CommonJS:* Nest 12 still supports it through `require(esm)`, but it would mix module formats in one repo and bring Jest next to Vitest.
- *Alternative — writing the files by hand:* teaches the same files, but the ESM tsconfig and the test setup are easy to get wrong; reading the generated files is the better first look.

After generating: rename the package to `@closet/api`, mark it `private`, remove anything that belongs to the repo root (a nested `.git`, lockfile or workspace file), and run `pnpm install` from the root.

### 3. Each package keeps its own TypeScript
`apps/api` keeps the TypeScript version the Nest template installs (6.x — what the Nest CLI compiles with, including decorator metadata). `core` stays on TypeScript 7. Packages compile independently, and the API only reads `core`'s emitted `.d.ts` files, so the two versions don't meet.

### 4. Build `core` to JavaScript
- Switch `core` to `module` / `moduleResolution: "NodeNext"` and add `.js` to every relative import (`./vocabularies.js`). Node ES modules don't resolve extensionless paths; TypeScript maps `.js` back to the `.ts` file.
- Add `tsconfig.build.json` that emits `dist/` with declarations and excludes `*.test.ts`.
- Point `exports` at `dist`: `{ ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } }`.
- Core's own tests keep running on the source.
- *Alternative — bundle `core` (tsup, rolldown):* another tool for one small package.
- *Alternative — a custom `source` export condition* so dev tools read `src/` without a build: convenient, more configuration; worth revisiting if rebuilding gets annoying.
- *Alternative — `rewriteRelativeImportExtensions` with `.ts` imports:* write the real file name and let tsc rewrite it to `.js` on emit. Rejected because the Nest docs, templates and generators all use `.js`, so `apps/api` would mix two styles. Not a dead end: verified with TypeScript 7.0.2 that `.ts` and `.js` specifiers compile side by side, so the flag can be switched on later without touching existing imports.

Dev loop: `core` gets a `dev` script (`tsc --watch` with the build config); a root `dev:api` script builds `core` first, then starts Nest in watch mode.

### 5. Validation: the built-in Standard Schema pipe, registered as a provider
- Register `StandardSchemaValidationPipe` through the `APP_PIPE` provider in `AppModule`, **not** with `app.useGlobalPipes()` in `main.ts`. The e2e tests build the app from `AppModule` and never run `main.ts`, so a pipe registered there wouldn't exist in tests.
- Pass an `exceptionFactory` that turns the Standard Schema issues into the agreed body: `{ statusCode: 400, message: 'Validation failed', errors: [{ path, message }] }`. An issue's `path` is an array whose segments are either keys or `{ key }` objects; join the keys with dots.
- Keep `transform: true` (the default): the handler receives the schema's output, which is what drops unknown fields (zod objects strip keys they don't define).
- Attach schemas per parameter: `@Body({ schema: scoreOutfitRequestSchema })`. The parameter type is `z.infer<typeof scoreOutfitRequestSchema>`.
- *Alternative — `class-validator` DTO classes:* the Nest classic, but it would duplicate every rule already in `core`.
- *Alternative — a hand-written `ZodValidationPipe`:* what Nest 11 projects did; Nest 12 makes it unnecessary.

### 6. Configuration: `@nestjs/config` with a zod schema
`ConfigModule.forRoot({ isGlobal: true, validationSchema: envSchema })`, where `envSchema` lives in `src/config/env.ts`:
- `PORT`: coerced to a whole positive number, default 3000;
- `NODE_ENV`: `development` | `production` | `test`, default `development`.

`main.ts` reads the port through `ConfigService` (`get('PORT', { infer: true })` with a typed service). `.env.example` is committed; `.env` is already git-ignored.

### 7. The outfit endpoint
- `OutfitsModule` = `OutfitsController` + `OutfitsService`. The controller only translates HTTP; the service calls `checkHardFilters`, and `scoreOutfit` only when the filters pass. A service that just calls `core` looks thin now, but it's where history and the database plug in at step 10 — and it's the dependency-injection practice.
- Request schema (in the API): `{ occasion: occasionSchema, items: outfitItemSchema[] }` with 1–6 items.
- Response: `{ filters, score? }` — `score` is present only when `filters.ok` is true.

### 8. Core gains two schemas
In `core/src/scoring/schemas.ts`:
- `occasionSchema`: `code` from `OCCASIONS`, `targetFormality` on the 1–5 scale, optional `weights` keyed by `COMPONENTS` with non-negative numbers (zod 4: `z.partialRecord`).
- `outfitItemSchema`: `itemTagsSchema` plus a non-empty `id`. Use `.safeExtend()`: in zod 4, `.extend()` throws on an object schema that has refinements, and `itemTagsSchema` has one.
- Derive the `Occasion` and `OutfitItem` types from these schemas (`z.infer`) and delete the hand-written ones, so types and validation can't drift.

### 9. Documentation: the built-in Standard Schema hook, fed by zod itself
`@nestjs/swagger` 12 takes a `standardSchemaConverter` in `SwaggerDocumentOptions`: a function
`(schema, { schemaType }) => { schema, components } | undefined` that it applies to every schema attached to a
route decorator. Returning `undefined` falls back to the class-derived schema, so one type guard on the
`~standard` vendor tag is enough to handle only ours.
- The converter is `z.toJSONSchema(schema, { target: 'openapi-3.0', io: schemaType, unrepresentable: 'any' })`.
  zod 4 emits OpenAPI 3.0 by itself, so the `zod-openapi` package the official example suggests is not needed.
  `unrepresentable: 'any'` is required: `itemTagsSchema` carries a refinement, which JSON Schema cannot express,
  and without the option the conversion throws instead of relaxing that one field.
- `setupOpenApi(app)` lives in `src/docs/openapi.ts` and is called from `main.ts` **and** from the e2e setup.
  Swagger is not a provider, so `APP_PIPE`-style registration does not apply; the tests build the app from
  `AppModule` and never run `main.ts`, so they call the same exported function.
- *Alternative — `zod-openapi` or `@nestm/standard-schema`:* a dependency and a prerelease respectively, for what
  zod already does.
- *Alternative — `class-validator` DTOs so Swagger can reflect classes:* the duplication decision 5 already rejected.

### Target structure (orientation)

```
apps/api/
  package.json              "@closet/api", "type": "module", depends on "@closet/core": "workspace:*"
  nest-cli.json, tsconfig.json, vitest config   from the template
  .env.example
  src/
    main.ts                 create the app, read PORT from ConfigService, listen
    app.module.ts           ConfigModule, HealthModule, OutfitsModule, APP_PIPE
    config/env.ts           envSchema + Env type
    docs/openapi.ts         zod to OpenAPI converter + setupOpenApi
    validation/validation-exception.ts   issues → { path, message }[]
    health/                 health.module.ts, health.controller.ts
    outfits/                outfits.module.ts, outfits.controller.ts, outfits.service.ts, score-outfit.request.ts
  test/                     e2e tests (written by Claude)
```


### Common pitfalls
- **A `POST` route answers 201 by default** — the spec says 200, so add `@HttpCode(200)`.
- **A pipe registered in `main.ts` is missing in tests** — use `APP_PIPE`.
- **Missing `.js` in a relative import** compiles but fails at runtime with `ERR_MODULE_NOT_FOUND`.
- **Forgetting to rebuild `core`** — the API keeps running the old `dist/`. Use the `dev` watch script.
- **`.extend()` on `itemTagsSchema` throws** — use `.safeExtend()`.
- **Config is read when `AppModule` is imported** — `ConfigModule.forRoot()` runs at import time, so environment variables must be set before that.
- **pnpm 12 blocks dependency build scripts** — if an install stops, approve only what's needed with `pnpm approve-builds`.
  `@nestjs/swagger` pulls in `@scarf/scarf`, install-time analytics, which is denied in `pnpm-workspace.yaml` rather than approved.
- **Swagger set up only in `main.ts` is invisible to the e2e tests** — the same trap as the pipe, with a different fix: export a function and call it from both places.

## Risks / Trade-offs

- [Nest 12 is recent; the generated template may differ from the docs] → follow the generated files and adjust this plan with `/opsx:update` if needed.
- [Two TypeScript versions in one repo] → each package type-checks with its own compiler; `pnpm typecheck` runs both.
- [`core` now needs a build before the API runs] → the `dev:api` root script and the `core` watch script; the `source` export condition remains an option.
- [`POST /outfits/score` is open without authentication] → it stores nothing and does pure computation; authentication arrives at step 4, rate limiting with it.
